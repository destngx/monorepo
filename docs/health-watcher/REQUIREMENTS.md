## 1. Product summary

- **Problem**: health results arrive from dentists, hospitals and clinics as printed pages, PDFs, record books, photos and imaging films. They sit on a bookshelf. Finding an old CT report means searching by hand, and lab values can't be compared across years.
- **Users**: a family or another small group. One person may manage records for others (children, parents), and one login may belong to more than one group.
- **What the app does**, in priority order:
  1. Stores every original (paper scan, PDF, photo, film photo) with its date, person, provider and type, so any record can be found by search.
  2. Reads each document into structured data: lab values with units and the reference range printed on that paper, diagnoses, prescriptions and procedures. A person approves every reading before it counts.
  3. Draws each metric over time, across clinics, with its reference range.
  4. Gives an AI review of the approved data. Each comment cites its source. The review is for reference only and never replaces a doctor.
- **Not in scope**: diagnosis, treatment advice, reading medical images with AI, sharing with clinics, native mobile apps (iOS installs need a paid developer account, see D2).
- **Locale**: documents are mostly Vietnamese, some English. Timezone `Asia/Ho_Chi_Minh`. Dates show as `dd/MM/yyyy`.
- **Architecture**: one Nx project `health-watcher` at `apps/health-watcher/`. The Go engine sits at the project root (hexagonal: `domain/`, `port/`, `service/`, `adapter/`). The SvelteKit UI lives in `ui/`, built as a static SPA (`adapter-static`, base `/ui`) and served by Fiber. One process, one origin, the same as wealth-management.

## 2. Tenants and people

A **tenant** is a family or group. Everything the app stores belongs to exactly one tenant.

| ID       | Requirement                                                                                                                                                                                                                                                        | Status |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------ |
| HW-TEN-1 | **Tenant**: has a name (e.g. `Nguyen family`). The user who creates it is its first owner.                                                                                                                                                                         | ✅ B   |
| HW-TEN-2 | **Membership**: a user belongs to one or more tenants with a role. `owner` manages members and settings and can delete the tenant. `editor` adds, edits and approves records. `viewer` only reads. A tenant always keeps at least one owner.                       | ✅ B   |
| HW-TEN-3 | **Person**: the subject of records. A person belongs to one tenant and has a display name, date of birth and sex at birth (reference ranges depend on both). A person may be linked to a user (an adult who logs in) or not (a child, a parent who never logs in). | ✅ B   |
| HW-TEN-4 | **Invites**: an owner creates a one-time invite link with a role, valid for 7 days. Opening it signs in or registers the user and adds the membership.                                                                                                             | ✅ B   |
| HW-TEN-5 | **Tenant switch**: a user in several tenants picks the active tenant in the header. The choice is kept per browser. Every request carries the active tenant, and the engine checks the membership on each request.                                                 | ✅ B   |
| HW-TEN-6 | **Isolation**: every table that holds tenant data has a `tenant_id` column. Repositories take the tenant from the request scope and never accept it from the request body. A test suite proves a member of tenant A gets `404` for every resource of tenant B.     | ✅ B   |

## 4. Records model

```
Tenant ─┬─ Person ─┬─ Visit (date, provider, specialty, note)
        │          │    └─ Document (one original file, its pages and OCR text)
        │          │         ├─ Observation (one measured value)
        │          │         └─ Finding (diagnosis, prescription, procedure, imaging report)
        │          └─ Review (an AI review of approved data)
        └─ Provider (hospital, clinic, dentist, lab)
```

| ID       | Requirement                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   | Status |
| -------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------ |
| HW-REC-1 | **Visit**: one encounter on one date with one provider for one person. Type is one of `checkup`, `lab`, `imaging`, `dental`, `specialist`, `emergency`, `inpatient`, `vaccination`, `other`. A visit can exist with no documents. An inpatient stay can have an end date, which must not fall before the visit date (FHIR `Encounter.period`).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                | ✅ B   |
| HW-REC-2 | **Document**: one original, kept byte for byte (HW-OPS-2). Kind is one of `lab_result`, `imaging_report`, `imaging_film`, `prescription`, `discharge_summary`, `dental_record`, `record_book_page`, `invoice`, `other`. A document has pages, and each page has OCR text. A document can carry the date printed on it when that differs from the visit date, as lab results printed days later do.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            | ✅ B   |
| HW-REC-3 | **Observation**: analyte, value (number, or text for results like `Âm tính`), unit, the reference range printed on the paper (low, high, or text), the paper's own flag (H, L, `*`), the sample date and the source document and page. Linked to the metric catalog (HW-MET-1) when the analyte is known.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     | ✅ B   |
| HW-REC-4 | **Finding**: kind (`diagnosis`, `exam`, `prescription`, `procedure`, `imaging_report`, `advice`, `allergy`, `vaccination`, `note`), the section it was written under (the specialty or body system of an exam, the study of an imaging report), text as written with its line breaks, an optional ICD-10 code when the paper prints one, and the source document and page. Prescriptions keep drug, dose, frequency and duration; vaccinations keep the vaccine and the amount given. Any finding can keep the date written beside it, such as the day of one vaccine dose; without one it takes the visit date.                                                                                                                                                                                                                                                                                                                              | ✅ B   |
| HW-REC-5 | **Provider**: name and kind (`hospital`, `clinic`, `dental`, `lab`, `pharmacy`, `other`) per tenant. Names are matched ignoring case, Vietnamese accents and spacing, so `BV Chợ Rẫy` and `BV CHO RAY` are one provider.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      | ✅ B   |
| HW-REC-6 | **Edits and history**: approved observations and findings can be edited or deleted by editors. Every change keeps who, when, and the old value in an audit table. Each edit of an approved record raises its version, and each audit entry keeps the version its old value had (FHIR `meta.versionId`).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       | ✅ B   |
| HW-REC-7 | **FHIR R4 alignment** (D9): every record maps to one FHIR R4 resource as [DATA-MODEL.md](./DATA-MODEL.md) lists, with codes from LOINC, UCUM, ICD-10 and the HL7 code systems (`domain/terminology.go`). Each observation and finding keeps its version, its source (`reading`, `manual`, `import`), the reading's model, and who approved it and when. Records from before D9 got their source and version from the readings and the audit log; their approver is unknown until an editor checks the document and presses _I checked them_, which records them as the approver without a new version. Fields a complete export needs stay optional while working; each record reports the ones it lacks (`exportGaps`: an inpatient stay's last day, an approver), and the visit and document pages say what to fill in. The visit form asks for the last day of an inpatient stay, and the document form for the date printed on the paper. | ✅ B   |

## 6. Reading documents

| ID         | Requirement                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  | Status |
| ---------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------ |
| HW-READ-1  | **Local text first**: a background worker runs every file through `mac-ocr` (`--lang vi-VT,en-US`, JSON output). PDF text layers are used when present, OCR otherwise. Page text is stored and indexed for search (HW-FIND-2) without any AI call.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           | ✅ B   |
| HW-READ-2  | **Page images**: each PDF page is rendered to a JPEG for the viewer and for AI reading (D4).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 | ✅ B   |
| HW-READ-3  | **AI reading**: the worker sends the page images and OCR text to the AI provider (HW-AI-1) with a strict JSON schema. The reading proposes: person (from the name on the paper, matched to the tenant's people), date, provider, visit type, document kind, observations (HW-REC-3) and findings (HW-REC-4). Findings include each specialty's exam result and comment, the doctor's advice, and each imaging report's description and conclusion. The model never describes a medical image itself (D5). Each value carries the page it came from and a confidence from 0 to 100. Images and text go in one request, both masked first (HW-AI-7): the image fixes OCR misreads and the text pins exact digits (D6). Person, birth year and sex come from the local match, never from the model. A result printed as a number with its reading, such as `Negative 0.794` S/Co, keeps only the number; the prompt asks for that and the engine strips a reading the model left in.                                                                                                                                                                                            | ✅ B   |
| HW-READ-4  | **Drafts and approval**: an AI reading becomes drafts, never records. The review page shows the page image beside the drafts, highlights low-confidence values, and lets the user edit, approve or reject. Nothing counts in charts or reviews until approved. An editor can remove one page of an unfiled item, as on a filed document (HW-FIND-3): its drafts are deleted, a file left with no pages leaves the item, and a finished reading runs again without the page, replacing the drafts. The last page goes only with the item.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     | ✅ B   |
| HW-READ-5  | **Units and analyte matching**: on reading, each analyte name is matched to the metric catalog by its known names in Vietnamese and English (`Glucose`, `Đường huyết`, `GLU`). An unmatched analyte stays as written and can be linked to a catalog entry by hand. The link is remembered for that provider. A count's name never matches a longer name by its start: `Số lượng bạch cầu đoạn` and `Số lượng bạch cầu Mid` are not the white cell count. A text result such as `Âm tính` picks a test read as text, so a urine strip's `Bạch cầu` is not the blood count. When the catalog changes, the engine matches approved values again at start, including values it relinked before; a value a person edited, or a name a person linked by hand, keeps its link, and each change shows in the value's history.                                                                                                                                                                                                                                                                                                                                                        | ✅ B   |
| HW-READ-6  | **Retries**: provider failures retry with backoff (1, 5, 30 minutes, then 6 hours), up to 5 attempts, then the item is marked failed with the error and a _Retry_ button. With AI not configured, items stay at OCR-only and can still be filed by hand; when an admin turns AI on, every unfiled item whose reading is off is sent, with no _Retry_ needed.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 | ✅ B   |
| HW-READ-7  | **Manual entry**: a visit, document metadata, observations and findings can all be entered by hand, without AI.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              | ✅ B   |
| HW-READ-8  | **Back to inbox**: a filed document with no values or findings has a _Back to inbox_ button. Its item returns to the inbox with its files and masks, the empty document is removed and the visit stays, so the item is read with AI and filed again. An item read while AI was off is sent as soon as it returns. A document with values is refused, so no approved record is lost; film photos (D5) have no button.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         | ✅ B   |
| HW-READ-9  | **Page titles**: every page has a title. The AI reading gives each page a short title in the document's language, such as `Tổng phân tích tế bào máu`, from its printed heading when there is one, never with personal details. A page the AI leaves without a title goes back to it, with its masked text alone, up to two more times; after that the reading fails and retries like any other failure (HW-READ-6). A page with too little text to send is titled _Photo or blank page_. Pages show `Page 2 · title` wherever they are named. Filing a document, and each engine start, queue a title job for pages still without one. The job sends only masked text: a page keeps the mask it was read with, a page never masked is masked first, and a page whose mask needs a check waits until a person checks it on the document page with _It looks right_.                                                                                                                                                                                                                                                                                                          | ✅ B   |
| HW-READ-10 | **Vaccine record books**: each dose line with a date (`Lần 1`, `Nhắc`) is one vaccination finding: section the disease as printed, the vaccine as written in its column, the amount given and that dose's date. A test result written beside the disease is a note. Record books write every planned date in advance, so a date alone, even a past one, does not show a dose was given: the model names the mark beside each dose line that shows it was given (a clinic stamp, a signature or initials in the doctor column, a vaccine sticker), never a black privacy box. A dose with a mark and a date not after the day of reading is a vaccination; any other becomes advice that the dose is due, with its date and the vaccine leading the text. Vaccine names are often faint stamps the model misreads with high confidence (D12): a dose takes the vaccine of the person's latest approved dose for the same disease, and a name no earlier dose confirms is capped at 60% confidence so the review page asks for a check. Every dose read as given is capped the same way, since the model sometimes takes a signature beside one dose for the mark of the next. | ✅ B   |

## 11. Architecture

- **Engine**: Go, Fiber v2, `log/slog`, `modernc.org/sqlite`, `golang.org/x/crypto/argon2`. `internal/app` wires the services for `main.go` and the commands. Routes are plain Fiber routes; an OpenAPI document can follow when an outside client needs one. The records model follows FHIR R4 (D9, [DATA-MODEL.md](./DATA-MODEL.md)); the app's JSON API keeps its own shapes, and a FHIR API (HW-INT-1) would map them.
- **Layers**: `domain/` (types and rules, no I/O), `port/` (interfaces: repositories, file store, OCR, AI), `service/` (use cases; every method takes a `domain.Scope` holding the user, tenant and role), `adapter/` (sqlite, filestore, macocr, ai/openai, fiber).
- **Tenant scope**: a Fiber middleware resolves the session and the active tenant into a `domain.Scope` and puts it in the request context. Services read the scope, check the role, and pass `scope.TenantID` to repositories. Repositories have no method that reads tenant data without a tenant id.
- **Workers**: one in-process worker pool for OCR, page rendering and AI reading, driven by a `jobs` table (status, attempts, `next_attempt_at`), so work survives restarts.
- **UI**: SvelteKit with runes, Tailwind v4, hand-made components in `ui/src/lib/components`, fetch client with typed `ApiError` (copied from wealth-management, not shared, until a shared lib is worth it). Charts follow the repo's dataviz guidance.

Records stay in typed SQLite tables, each mapped to one FHIR resource, with standard codes, versions and provenance ([DATA-MODEL.md](./DATA-MODEL.md)). National identifiers (CCCD, BHYT) are not stored for now, so patients conform to base R4, not the VN Core Patient profile. Imported data will land as drafts and be approved in bulk. Output will be checked against the official R4 JSON schema in tests, with no Java validator. Rejected: storing raw FHIR JSON per resource (trends and search need typed columns), renaming the app's words to FHIR names (the UI speaks of visits and documents, and the mapping table is the contract).                                                                                                                                            |
| D11 | How new metrics join the catalog.          | **Decided 2026-10-23**: the app suggests and a person approves. The user won't know when a paper prints a test the catalog lacks, so the app checks after each filing. The AI gets printed names and units only. A new metric lives in the tenant's database with its LOINC code checked against NLM, instead of a code change to the shipped catalog. Rejected: matching by hand only, and a release for each new test.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| D12 | How vaccine names are read.                | **Decided 2026-10-24**: the model reads the name and the person's history checks it. On a real record book the model read a faint stamped vaccine name as the OCR's fragment or as better-known brands, usually at 90% or more, at every reasoning effort and from enlarged crops of the page; Apple Vision misread it too. So a name no earlier approved dose for the same disease confirms is flagged for a check, and a later dose takes the earlier dose's name, also flagged when the model read something else. Whether a dose was given is read the same way: on two real record books the model named the right mark in about three runs of four, and a wrong "given" shows protection a person lacks, so every dose read as given is flagged, while a wrong "due" only adds a reminder. Rejected: sending enlarged parts of each page (closer reads, never right, about ten times the image tokens) and snapping names to a list of known vaccines (it would turn a misread into a wrong brand without a flag). |
