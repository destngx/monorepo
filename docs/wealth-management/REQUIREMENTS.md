## 1. Product summary

- **User**: a single user managing personal wealth in VND (bank accounts, credit cards, crypto, Vietnamese fund certificates (IFC/CCQ), SJC gold, money lent to people, savings goals). Single-tenant, no multi-user.
- **System of record**: one Google Sheet (`GOOGLE_SHEETS_ID`). The app reads and writes the sheet; it never owns financial data itself. Sheet formulas (e.g. GOOGLEFINANCE USD/VND conversion, account balances) are part of the system and must not be bypassed.
- **Value**: one place to see net worth, cash flow, budget burn, card cashback efficiency, debts and goals; fast transaction entry (manual or from parsed bank emails); and AI/market intelligence for VN investments.
- **Base currency**: VND (`vi-VN` formatting, 0 decimals). Timezone `Asia/Ho_Chi_Minh`. UI language mixes EN and VI.
- **Target architecture** (decided, mirrors the graph-weave consolidation in `13c544a`): one Nx project `wealth-management` at `apps/wealth-management/`: Go engine at the project root, SvelteKit UI in `ui/` built as a static SPA (`adapter-static`, base `/ui`) and served by Fiber. One process, one origin in production. MCP server exposes the same capabilities to external agents.

### 5.2 Credit cards and cashback (`/accounts/credit-cards`, `/accounts/credit-cards/:name`)

The schema below is derived from these needs and facts; a change to a need or fact comes first, then the schema follows. Agreed with the user on 2026-10-15.

**Needs (why)**

| #   | Need                                                                                                                                               |
| --- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| N1  | Know what each payment earns under the bank's rules.                                                                                               |
| N2  | Check each month's cashback refund against what was expected, to spot underpayment.                                                                |
| N3  | Know where each card stands in the period: cap left, distance to the next spend tier.                                                              |
| N4  | Choose the best held card for a merchant before paying.                                                                                            |
| N5  | Compare programmes, including cards not held: what each would have earned on my last 12 months of spending, and a ranking for my spending pattern. |
| N6  | Know whether each card's annual fee pays off.                                                                                                      |
| N7  | Never pay late: every card is paid by day 29 of each month (28 in February).                                                                       |
| N8  | Card and programme details stay out of the public repo.                                                                                            |
| N9  | Keep usage well below the limit unless needed, measured against a reference limit (20,000,000 VND today).                                          |

**Domain facts**

| #   | Fact                                                                                                                                                                                                                                                                         |
| --- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| F1  | The bank decides the rate by the MCC of the merchant's terminal. The programme document lists the MCCs of each category.                                                                                                                                                     |
| F2  | A store's MCC is not shown to the cardholder; the monthly statement lists transactions without MCCs (confirmed by the user).                                                                                                                                                 |
| F3  | An MCC belongs to a terminal, not a brand: one merchant can have several (online, in store) and can change it (new acquiring bank).                                                                                                                                          |
| F4  | Cashback is reported as one total per month, not per transaction.                                                                                                                                                                                                            |
| F5  | Conditions stack: category rates, minimum transaction, spend tiers, caps per category and per card, and excluded MCCs.                                                                                                                                                       |
| F6  | Banks revise programmes; a past month is judged by the terms in effect then.                                                                                                                                                                                                 |
| F7  | Each programme document states whether caps and tiers count per statement cycle or per calendar month. Today's card: statement issued on day 5, cashback counted per statement period (5th to the 4th of the next month), payment due before day 30 (confirmed by the user). |
| F8  | The cards of one bank share one credit limit and one usage.                                                                                                                                                                                                                  |
| F9  | Paying in more than is owed raises the spending room; there is no fixed maximum, so an account can be in credit (positive balance).                                                                                                                                          |

**Design rules (how, derived)**

| #   | Rule                                                                                                                                                                                                     | From       |
| --- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------- |
| C1  | A programme (the bank's terms) is separate from a card (what I hold), so programmes not held can be evaluated.                                                                                           | N5         |
| C2  | Programmes are versioned: each version is a full copy of the terms from a date. Old versions are never edited.                                                                                           | F6         |
| C3  | Rules match by MCC lists copied from the bank document. Tags no longer pick rates; card tags only say which card paid.                                                                                   | F1         |
| C4  | Store MCCs are dated observations with a confidence (`assumed` or `confirmed`). An `mcc:NNNN` tag on a payment is confirmed for that payment.                                                            | F2, F3     |
| C5  | Every cashback figure splits into confirmed (all MCCs involved confirmed) and estimated (assumed or unknown MCC; unknown earns the fallback rate).                                                       | N1, F2     |
| C6  | Reconciliation is per month total: expected (confirmed + estimated) vs the refund. A mismatch flags the month; it cannot point at a payment, so confirming a merchant's MCC is a manual act.             | N2, F4     |
| C7  | The counting period is a required field of each programme version, never assumed.                                                                                                                        | F7         |
| C8  | The pay-by date is day 29 of each month (28 in February), strictly; it does not follow the bank due day.                                                                                                 | N7         |
| C9  | The credit limit and usage belong to the bank, not the card: a `Banks` tab holds the shared account and the reference limit. Usage = max(0, −balance), so money paid in ahead counts as room, not usage. | N9, F8, F9 |

**Implementation choices** (not dictated by a need; revisit if one proves wrong)

| #   | Choice                                                                                                                                                           |
| --- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| I1  | A refund belongs to the period that starts in its effective month (WM-RULE-4: the memo month, else the date).                                                    |
| I2  | A programme version that starts mid-period is counted as its own period from that date, so caps and tiers do not mix terms.                                      |
| I3  | Period standing includes later-dated (planned) payments of the current period.                                                                                   |
| I4  | Comparison (WM-CARD-14) uses each programme's current version (else its first), the statement day of a card holding it (else the 1st), and held cards' payments. |
| I5  | A bank with no held card is left out of the reports; a bank with no limit set never blocks a suggestion.                                                         |
| I6  | Untagged spend on a shared account counts for that bank's default card; Smart Capture suggests card keywords as tags.                                            |
| I7  | A closed card's lifetime fees stop at the closing date; a fee it paid this year still counts in fees paid YTD.                                                   |

**Implementation notes** (engine `service/ai/capture.go`, `domain/capture*.go`; UI `/transactions/capture`):

- The model only reads materials: one vision call per material (3 in parallel) with prompt `tasks/capture-extract` (variables `{{today}}`, `{{accounts}}`, `{{aliases}}`) plus the engine's JSON contract. Text materials are PII-masked first.
- Consolidation, account matching (alias rules, last-4 digits, distinctive name words), own-transfer pairing, ledger dedup and balance reconciliation are deterministic engine code, so `tasks/capture-consolidate` is not used: the same inputs always give the same suggestions.
- Payees: a `counterparty` rule replaces the material's name with the payee the user writes for it (WM-CAP-23), before lending matching and categories.
- Categories: lending payee match and lending note (WM-CAP-22) → `CaptureRules` payee rule → payee history → one batched model call with the optional prompt `tasks/capture-categorize` (variable `{{categories}}`; validated against the category list and the card's cashback tags) → `Uncategorized`, flagged for review.
- `CaptureRules` tab (created on first save): `Kind | Pattern | Value | Updated`, kind `alias` (pattern → account), `payee` (payee → category) `counterparty` (the name a material shows → payee, saved automatically from written rows, WM-CAP-23) or `screen` (a label an app shows on screen → the account its screenshots are mostly from, WM-CAP-4); matching ignores case and Vietnamese accents, and counterparty patterns also ignore words with digits and generic transfer words. HTTP `GET/POST /api/capture/rules`, MCP `GetCaptureRules` / `SaveCaptureRules`.
- `POST /api/ai/capture` streams NDJSON progress events then `{"type":"result"}`; MCP `SuggestTransactionsFromMaterials` returns the same result. Neither writes; commits use `POST /api/transactions/batch`, then the page sends the written rows to `POST /api/capture/learn` (WM-CAP-23).
- Materials live in the browser tab and the request only; the engine never logs, caches or writes them. Quick capture (§6.3) is the one exception, and capture memory (WM-CAP-23) keeps the text read for written rows in the same private store.

### 6.3 Quick capture and drafts

Capture happens on the iPhone at the moment the user checks a bank or wallet app; review happens later. One AssistiveTouch tap runs an iOS Shortcut that screenshots the current screen and sends it to the engine; the engine turns it into **draft transactions** in the background; the user approves or rejects drafts when convenient. Drafts are never committed automatically: the §6.2 approval rule holds. See D29 for why notification-based routes were rejected.

**Flow**: AssistiveTouch → Shortcut (screenshot, POST) → capture inbox → background Smart Capture pipeline → drafts → review on `/transactions/drafts` → approve (batch create) or reject → material deleted.

## 10. AI

### 10.1 Architecture (decided)

The engine removed its in-process LLM layer on 2026-04-02 (`f4ec0ec`) in favour of MCP-first. Revision 2 brings in-app AI back: **all AI features from the legacy app (analysis, reviews, briefings, advisor, chat, think tank) are in scope and run inside the engine**, plus Smart Capture (§6.2).

- **Engine `ai` port** (hexagonal): `Complete`, `CompleteJSON` (schema-validated), `Stream`, tool calling, and **image input** (required by Smart Capture). One adapter behind it for the OpenAI Responses API; the provider is OpenAI only, reached through ai-gateway (every call sends `X-AI-Provider: openai`) or the official API (D10).
- **Deterministic first**: every number (net worth, budget actuals, health score, cashback, technicals) is computed by the engine (§12) and passed to the model as facts. The model explains and recommends; it never computes ledger figures.
- **MCP stays** as the interface for external agents, exposing the same data and the same AI use cases.
- One AI use-case service per feature, each with: prompt keys, input builder, output schema, cache policy, and tests against a stubbed `ai` port.

**Configuration** (engine settings, edited on the Settings page; WM-SET-5). AI is disabled, and `GET /api/ai/status` says why, until `AI_BASE_URL` and `AI_MODEL` are set; the AI routes need the Google Sheet because prompts and data come from it.

| Variable                                                                   | Meaning                                                                                                                                                 |
| -------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `AI_BASE_URL`                                                              | OpenAI Responses API base URL (`POST {AI_BASE_URL}/responses`), e.g. `http://127.0.0.1:8081/v1` for ai-gateway.                                         |
| `AI_API_KEY`                                                               | Bearer key for the provider (optional for a local gateway).                                                                                             |
